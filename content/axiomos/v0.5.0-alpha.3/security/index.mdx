axiomos positions itself in the **engineering-safety** class: a memory-safe implementation language, a load-bearing static verifier with zero `unsafe`, WCET admission control, an inventoried unsafe surface and a growing test corpus, but **no** machine-checked proofs of the kernel, no verified scheduler, and no external audit yet ([SECURITY.md](https://github.com/pro-utkarshM/axiomOS/blob/release/v0.5.0-alpha.3/SECURITY.md)).

## Security bug priorities

Per [SECURITY.md](https://github.com/pro-utkarshM/axiomOS/blob/release/v0.5.0-alpha.3/SECURITY.md), in rough priority order:

1. **Verifier soundness:** a program that passes verification but reads/writes outside verified regions, overflows the stack, exceeds its execution bound, or bypasses a helper argument contract.
2. **Syscall boundary:** userspace input that corrupts kernel state through `sys_bpf` or any other syscall.
3. **Isolation:** a BPF program observing or modifying another program's or the kernel's state outside the helper API.
4. **Denial of service from unprivileged input** (verifier state explosion, unbounded admission).

Out of scope today: speculative-execution side channels (#89) and physical attacks (JTAG, SD-card swap). Reports go to the address in SECURITY.md with subject `[axiomos-security]`, or via GitHub private vulnerability reporting.

<Callout type="warning">
Several security documents were written at different points in an ongoing audit remediation and partly disagree. In particular, SECURITY.md and the threat model still say signature enforcement is off by default, while the normative [BPF trust policy](https://github.com/pro-utkarshM/axiomOS/blob/release/v0.5.0-alpha.3/docs/security/bpf-trust.md) and `kernel/src/bpf/trust.rs` make non-test builds without `bpf-unsigned-development` **signed-only**. Following the repository's own authority order, this wiki treats the normative trust policy and code as current.
</Callout>
