## Map types

Four map types can be created at runtime through `BPF_MAP_CREATE` (`BpfManager::create_map_for`). Any other type value returns `InvalidInstruction`.

| Type | Value | Constraints at creation | Storage and behaviour |
|---|---:|---|---|
| Hash (`BPF_MAP_TYPE_HASH`) | 1 | non-zero key and value size | One flat buffer of `state, key, value` buckets with linear probing; fixed key and value sizes |
| Array (`BPF_MAP_TYPE_ARRAY`) | 2 | key size must be 4, non-zero value size | Contiguous value bytes indexed by `u32` |
| Ring buffer (`BPF_MAP_TYPE_RINGBUF`) | 27 | key size 0, value size 0, `max_entries` a power of two (it is the byte size) | Reserve, submit and poll with an 8-byte event header; polling copies one committed event and advances the tail; nonblocking |
| Time series (`BPF_MAP_TYPE_TIMESERIES`) | 100 | key size 8 (a timestamp), non-zero value size | Circular storage of timestamped fixed-size values |

The `kernel_bpf::maps::MapType` enum names more types (prog array, per-CPU maps, stack trace, cgroup array, and cloud-only LRU hash, LRU per-CPU hash and LPM trie) so that ELF map definitions can be parsed, but the manager does not create them. The ABI catalog lists only the four above.

All constructors validate dimensions, use checked arithmetic for allocation sizes and reserve memory fallibly, returning `MapError` on invalid or exhausted requests. The `resize` operation exists only in cloud builds. Embedded constructors additionally reject any single map whose full allocation exceeds `MEMORY_BUDGET` (64 KiB). There is no static map pool.

### Reserved envelope map

Handle 0 (`ENVELOPE_MAP_ID`) is a kernel-owned, read-only envelope map created at manager construction from the profile's actuation constants. `RESERVED_MAP_COUNT` is 1, so user maps start after it. Mutating helpers on this handle are rejected by the verifier (read-only) and at runtime.

### Access and sharing

The verifier receives the caller's authoritative view of map sizes, generations and permissions (`MapPerm`: `Unavailable`, `ReadOnly`, `WriteOnly`, `ReadWrite`), and `ProgramRuntime` retains only the maps a program references and is authorized to use. At run time helpers re-resolve the handle through the program's captured map set and re-check access. During execution each map is leased (`MapLease`, up to 128 leases per execution); userspace mutation or destruction of a leased map fails rather than blocks. Pinning and cross-process grants are described in [Trust Model](/axiomos/fpga-bringup/bpf/trust-model).

## Helper functions

Helper IDs are defined once in `kernel_abi` and mirrored by the verifier's `HelperId` enum, which is also what the loader relocation table, the WCET cost table and the interpreter dispatch use. The loader source states the IDs are the kernel's own runtime ABI, not the upstream Linux uapi numbering; rkBPF extensions start at 1000.

The table lists every ID in `HelperId`. "Runtime" says whether the interpreter implements it; the others are known to the verifier and signature table but return `InvalidHelper` if executed. Tier is the minimum caller tier (`P` = privileged). "Act." marks helpers that require the actuation capability.

Which helpers the ABI catalog advertises as supported: `bpf_ktime_get_ns`, `bpf_trace_printk` (cloud profile only), map lookup/update/delete, `bpf_ringbuf_output`, `bpf_timeseries_push`, `bpf_get_interrupt_latency_ns`, `bpf_get_boot_time_ms`, `bpf_get_kernel_heap_kb`, `bpf_get_kernel_image_mb`, and, on Raspberry Pi 5, `bpf_gpio_set`, `bpf_gpio_get`, `bpf_pwm_write` and `bpf_motor_pair_v1` (experimental).

### Argument checking

Each helper has a `HelperSignature` of up to five argument types (`Scalar`, `PtrToMapKey`, `PtrToMapValue`, `PtrToStack`, `PtrToMem`, `MemSize`, `Const`, ring buffer types, and others) and a return type (`Integer`, `PtrToMapValueOrNull`, `PtrToAllocMemOrNull`, `Void`). Pointer returns become maybe-null pointers whose accessible size comes from the map's value size. Memory arguments paired with a size are bounds-checked against the pointed region.

### Actuation

Actuation helpers (`gpio_set`, `pwm_write`, `motor_pair_v1`, `can_send`) require both the verifier's `allow_actuation` flag (from the process `ACTUATE` capability at load time) and, at runtime, the ARM-A monitor in `kernel_bpf::actuation`. The profile supplies the envelope: on embedded a PWM duty ceiling of 90 percent and a slew limit of 20 per 1 ms window; on cloud these are no-op bounds. A program's authorization snapshot is stored with it, so later privilege changes do not widen an existing program. Kernel helpers `bpf_gpio_toggle` and `bpf_gpio_set_output` exist in `kernel/src/bpf/helpers.rs` but are explicitly not exposed to the BPF ABI.
